# 测试规范

本文档定义项目的测试开发规范和最佳实践

---

## 核心原则

### 测试驱动开发 (TDD)

测试不是事后补充，而是开发的第一步

TDD 循环：先写测试（Red）→ 运行失败（Red）→ 编写实现（Green）→ 测试通过（Green）→ 重构优化（Refactor）

---

## 新增功能的 TDD 流程

### 标准流程（五步法）

1. 先写测试 - 编写测试用例，描述期望行为
2. 确认失败 - 运行测试，确认红灯（测试失败）
3. 实现功能 - 编写最小实现，让测试通过（绿灯）
4. 重构代码 - 在测试保护下优化代码结构
5. 全部通过 - 确保所有测试通过，没有遗漏

### 实战示例：用户注册功能

**Step 1: 先写测试**

```java
@SpringBootTest
@ActiveProfiles("test")
class UserServiceTest {
    
    @Autowired
    private UserService userService;
    
    @Test
    @DisplayName("用户注册 - 成功场景")
    void testRegisterUser_Success() {
        // Given: 准备测试数据
        UserRegisterRequest request = new UserRegisterRequest();
        request.setUsername("testuser");
        request.setEmail("test@example.com");
        request.setPassword("Pass123!");
        
        // When: 执行注册
        UserBO result = userService.register(request);
        
        // Then: 验证结果
        assertNotNull(result);
        assertNotNull(result.getId());
        assertEquals("testuser", result.getUsername());
        assertEquals("test@example.com", result.getEmail());
        assertNull(result.getPassword()); // 密码不应该返回
    }
    
    @Test
    @DisplayName("用户注册 - 用户名已存在")
    void testRegisterUser_UsernameExists() {
        // Given: 准备重复的用户名
        UserRegisterRequest request = new UserRegisterRequest();
        request.setUsername("existinguser");
        
        // When & Then: 验证抛出异常
        assertThrows(ServiceException.class, () -> {
            userService.register(request);
        });
    }
}
```

**Step 2: 确认失败**
```bash
mvn test
# 预期结果：测试失败，因为 UserService.register() 方法还不存在
```

**Step 3: 实现功能**

```java
@Service
public class UserServiceImpl implements UserService {
    
    @Autowired
    private UserMapper userMapper;
    
    @Autowired
    private PasswordEncoder passwordEncoder;
    
    @Override
    @Transactional(rollbackFor = Exception.class)
    public UserBO register(UserRegisterRequest request) {
        // 1. 检查用户名是否已存在
        Long existingCount = userMapper.selectCount(
            new LambdaQueryWrapper<User>()
                .eq(User::getUsername, request.getUsername())
        );
        if (existingCount > 0) {
            throw new ServiceException("用户名已存在");
        }
        
        // 2. 创建并保存用户实体
        User user = new User();
        user.setUsername(request.getUsername());
        user.setEmail(request.getEmail());
        user.setPassword(passwordEncoder.encode(request.getPassword()));
        userMapper.insert(user);
        
        // 3. 转换为 BO 返回
        UserBO result = new UserBO();
        BeanUtils.copyProperties(user, result);
        result.setPassword(null); // 不返回密码
        return result;
    }
}
```

**Step 4: 重构优化**

```java
@Service
public class UserServiceImpl implements UserService {
    
    @Override
    @Transactional(rollbackFor = Exception.class)
    public UserBO register(UserRegisterRequest request) {
        validateUsernameUnique(request.getUsername());
        User user = createUserEntity(request);
        userMapper.insert(user);
        return convertToBO(user);
    }
    
    private void validateUsernameUnique(String username) {
        boolean exists = userMapper.exists(
            new LambdaQueryWrapper<User>()
                .eq(User::getUsername, username)
        );
        if (exists) {
            throw new ServiceException("用户名已存在");
        }
    }
    
    private User createUserEntity(UserRegisterRequest request) {
        User user = new User();
        user.setUsername(request.getUsername());
        user.setEmail(request.getEmail());
        user.setPassword(passwordEncoder.encode(request.getPassword()));
        return user;
    }
    
    private UserBO convertToBO(User user) {
        UserBO bo = new UserBO();
        BeanUtils.copyProperties(user, bo);
        bo.setPassword(null);
        return bo;
    }
}
```

**Step 5: 全部通过**
```bash
mvn test
# 预期结果：所有测试通过
```

## Bug 修复的测试先行流程

### 标准流程（四步法）

1. 先写复现测试 - 编写能复现 Bug 的测试用例（应失败）
2. 修复代码 - 修改代码让复现测试通过
3. 验证通过 - 确保修复后测试通过
4. 回归测试 - 运行所有测试，确保未引入新问题

### 实战示例：删除用户时未级联删除用户角色关联

**Step 1: 先写复现测试**

```java
@Test
@DisplayName("Bug修复 - 删除用户应级联删除用户角色关联")
void testDeleteUser_ShouldCascadeDeleteUserRoles() {
    // Given: 创建用户并分配角色
    User user = createTestUser("testuser");
    assignRole(user.getId(), "ROLE_USER");
    
    // 确认角色关联存在
    List<UserRole> roles = userRoleMapper.selectList(
        new LambdaQueryWrapper<UserRole>()
            .eq(UserRole::getUserId, user.getId())
    );
    assertEquals(1, roles.size(), "角色关联应该存在");
    
    // When: 删除用户
    userService.deleteUser(user.getId());
    
    // Then: 验证用户角色关联也被删除
    List<UserRole> rolesAfterDelete = userRoleMapper.selectList(
        new LambdaQueryWrapper<UserRole>()
            .eq(UserRole::getUserId, user.getId())
    );
    assertEquals(0, rolesAfterDelete.size(), "Bug: 角色关联应该被级联删除");
}
```

运行测试：失败 - 证实 Bug 存在

**Step 2: 修复代码**

```java
@Service
public class UserServiceImpl implements UserService {
    
    @Autowired
    private UserMapper userMapper;
    
    @Autowired
    private UserRoleMapper userRoleMapper;
    
    @Override
    @Transactional(rollbackFor = Exception.class)
    public void deleteUser(Long userId) {
        // 修复：先删除用户角色关联
        userRoleMapper.delete(
            new LambdaQueryWrapper<UserRole>()
                .eq(UserRole::getUserId, userId)
        );
        
        // 再删除用户
        userMapper.deleteById(userId);
    }
}
```

**Step 3: 验证通过**
```bash
mvn test -Dtest=UserServiceTest#testDeleteUser_ShouldCascadeDeleteUserRoles
# 预期结果：测试通过
```

**Step 4: 回归测试**
```bash
mvn test
# 预期结果：所有测试通过，未引入新问题
```

## 数据库测试规范

### 演示项目强制要求：H2 数据库优先

本项目是演示项目，测试必须使用 H2 内存数据库

⚠️ 禁止在演示项目中使用外部数据库（MySQL/PostgreSQL）

**为什么演示项目必须用 H2？**

1. 零依赖 - 用户下载代码后可直接运行测试，无需安装数据库
2. 隔离性 - 测试数据不污染开发环境
3. 可移植 - 跨平台、跨环境一致性好
4. 快速反馈 - 启动时间毫秒级，提升开发效率
5. CI/CD 友好 - 自动化测试管道无需配置外部数据库

**对比示例**：

使用 MySQL：
1. 安装 MySQL 服务器
2. 创建数据库
3. 执行 DDL 脚本
4. 修改配置文件
5. 运行测试
时间：5-10 分钟，容易出错

使用 H2：
1. mvn test
时间：5 秒，零配置

### 优先级策略

| 优先级 | 数据库 | 适用场景 | 演示项目建议 |
|-------|--------|---------|-------------|
| 首选（必须） | H2 | 单元测试 | 快速、隔离、零依赖 |
| 备选（不推荐） | SQLite | 集成测试 | 不适合演示项目 |
| 特殊（仅限特定场景） | MySQL/PostgreSQL | 数据库特定特性测试 | 不适合演示项目 |

⚠️ 演示项目禁用 MySQL/PostgreSQL 测试（除非测试数据库特定特性如 JSON 函数、全文索引）

### H2 配置（演示项目必须）

#### Maven 依赖（必须添加）

```xml
<!-- 演示项目必须添加 H2 依赖 -->
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>test</scope>
</dependency>
```

⚠️ 所有演示模块的 pom.xml 必须包含 H2 依赖

#### application-test.properties（演示项目标准配置）

```properties
# H2 内存数据库配置（演示项目标准配置）

# H2 内存数据库，MySQL 兼容模式（推荐）
spring.datasource.url=jdbc:h2:mem:testdb;MODE=MySQL;DB_CLOSE_DELAY=-1;DATABASE_TO_UPPER=false
spring.datasource.driver-class-name=org.h2.Driver
spring.datasource.username=sa
spring.datasource.password=

# 关键配置说明：
# - MODE=MySQL：启用 MySQL 兼容模式，支持大部分 MySQL 语法
# - DB_CLOSE_DELAY=-1：JVM 关闭前保持连接，避免多个 @Test 间数据库重建
# - DATABASE_TO_UPPER=false：保持表名字段名大小写不转换

# JPA 配置（如使用 JPA）
spring.jpa.database-platform=org.hibernate.dialect.H2Dialect
spring.jpa.hibernate.ddl-auto=create-drop

# MyBatis-Plus 配置（如使用 MyBatis-Plus）
spring.sql.init.mode=always
spring.sql.init.schema-locations=classpath:db/schema-h2.sql
```

配置提示：
- 复制上述配置到 `src/test/resources/application-test.properties`
- 测试类添加 `@ActiveProfiles("test")`
- H2 建表脚本放在 `src/test/resources/db/schema-h2.sql`

#### 测试基类

```java
@SpringBootTest
@ActiveProfiles("test")
@Transactional  // 测试后自动回滚
public abstract class BaseServiceTest {
    
    @BeforeEach
    void setUp() {
        // 测试前准备
    }
    
    @AfterEach
    void tearDown() {
        // 测试后清理（通常不需要，@Transactional 会自动回滚）
    }
}
```

### H2 与 MySQL 兼容性配置

#### 兼容性原则

演示项目的 DDL 脚本必须兼容 H2，避免使用 MySQL 特定语法

原则：
- 使用标准 SQL
- 避免 MySQL 特定语法（COMMENT、ENGINE）
- 避免 MySQL 特定函数（NOW()、CURRENT_TIMESTAMP 通用）
- 提供 schema-h2.sql（H2 建表脚本）

如需真实 MySQL 脚本：
- 提供 schema-mysql.sql（生产环境用）
- 提供 schema-h2.sql（测试环境用）

#### 建表脚本示例

**schema-h2.sql** (H2 建表脚本 - 演示项目必备)

```sql
-- H2 内存数据库建表脚本（演示项目标准）

-- 使用标准 SQL（H2 和 MySQL 都支持）
CREATE TABLE user (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) NOT NULL,
    password VARCHAR(255) NOT NULL,
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 外键约束（H2 支持）
CREATE TABLE user_role (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    FOREIGN KEY (user_id) REFERENCES user(id) ON DELETE CASCADE
);

-- 索引（H2 支持）
CREATE INDEX idx_user_username ON user(username);
CREATE INDEX idx_user_email ON user(email);

-- 如需自动更新时间戳，使用触发器（H2 支持）
CREATE TRIGGER trg_user_update_time 
BEFORE UPDATE ON user 
FOR EACH ROW 
CALL "SET NEW.update_time = CURRENT_TIMESTAMP";
```

**避免使用的 MySQL 特定语法**：
```sql
-- 以下代码会导致 H2 报错
CREATE TABLE user (
    id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '主键',  -- COMMENT 不被 H2 支持
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP  -- ON UPDATE CURRENT_TIMESTAMP 不被 H2 支持
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;  -- ENGINE/CHARSET 不被 H2 支持
```

#### H2 兼容性速查表

| SQL 特性 | H2 支持 | MySQL | 演示项目建议 |
|---------|---------|-------|-------------|
| AUTO_INCREMENT | ✅ | ✅ | 使用 |
| PRIMARY KEY | ✅ | ✅ | 使用 |
| FOREIGN KEY | ✅ | ✅ | 使用 |
| INDEX | ✅ | ✅ | 使用 |
| COMMENT | ❌ | ✅ | 避免（测试脚本中） |
| ENGINE=InnoDB | ❌ | ✅ | 避免 |
| CHARSET | ❌ | ✅ | 避免 |
| ON UPDATE CURRENT_TIMESTAMP | ❌ | ✅ | 用触发器替代 |
| CURRENT_TIMESTAMP | ✅ | ✅ | 使用 |
| NOW() | ✅ | ✅ | 使用 |
| DATETIME | ✅ | ✅ | 使用 TIMESTAMP 更通用 |

## 测试编写最佳实践

### 1. 测试命名规范

```java
// 好的命名：方法名_场景_预期结果
@Test
@DisplayName("用户注册 - 用户名已存在 - 应抛出异常")
void testRegisterUser_UsernameExists_ShouldThrowException() {
    // ...
}

// 差的命名：含糊不清
@Test
void test1() {  // 避免
    // ...
}
```

### 2. Given-When-Then 结构

```java
@Test
void testExample() {
    // Given: 准备测试数据和环境
    User user = new User();
    user.setUsername("test");
    
    // When: 执行被测试的操作
    UserBO result = userService.createUser(user);
    
    // Then: 验证结果
    assertNotNull(result);
    assertEquals("test", result.getUsername());
}
```

### 3. 测试覆盖范围

每个方法至少应测试：
- 正常场景（Happy Path）
- 边界条件（Boundary Conditions）
- 异常场景（Exception Cases）

```java
class UserServiceTest {
    
    // 正常场景
    @Test
    void testCreateUser_ValidInput_ShouldSuccess() { /* ... */ }
    
    // 边界条件
    @Test
    void testCreateUser_EmptyUsername_ShouldThrowException() { /* ... */ }
    
    @Test
    void testCreateUser_UsernameTooLong_ShouldThrowException() { /* ... */ }
    
    // 异常场景
    @Test
    void testCreateUser_UsernameAlreadyExists_ShouldThrowException() { /* ... */ }
}
```

### 4. 测试数据管理

```java
// 使用工厂方法或 Builder 模式
class UserTestDataFactory {
    
    public static User createDefaultUser() {
        User user = new User();
        user.setUsername("testuser");
        user.setEmail("test@example.com");
        user.setPassword("Pass123!");
        return user;
    }
    
    public static User createUserWithUsername(String username) {
        User user = createDefaultUser();
        user.setUsername(username);
        return user;
    }
}

// 测试中使用
@Test
void testExample() {
    User user = UserTestDataFactory.createDefaultUser();
    // ...
}
```

### 5. 断言最佳实践

```java
// 使用 JUnit 5 assertAll（推荐）
assertAll(
    () -> assertNotNull(result),
    () -> assertEquals("test", result.getUsername()),
    () -> assertEquals("test@example.com", result.getEmail())
);

// 避免：每个断言单独写（其中一个失败后，后续断言不会执行）
assertNotNull(result);
assertEquals("test", result.getUsername());
assertEquals("test@example.com", result.getEmail());
```

## 测试覆盖率目标

### 覆盖率要求

| 层级 | 覆盖率目标 | 说明 |
|------|-----------|------|
| Service 层 | ≥ 80% | 核心业务逻辑，重点覆盖 |
| Controller 层 | ≥ 70% | 接口层，包含参数校验测试 |
| Dao 层 | ≥ 60% | 数据访问层，复杂查询需测试 |
| Util 层 | 100% | 工具类，必须全覆盖 |

## 测试反模式（避免）

### 1. 测试依赖外部环境

```java
// 差的实践：依赖真实数据库、外部 API
@Test
void testGetUserFromRealDatabase() {
    User user = userMapper.selectById(1L);  // 依赖数据库中存在 id=1 的用户
    assertNotNull(user);
}

// 好的实践：使用 H2 内存数据库，测试前插入数据
@Test
void testGetUserFromDatabase() {
    // Given: 先插入测试数据
    User user = createTestUser("test");
    userMapper.insert(user);
    
    // When: 查询
    User found = userMapper.selectById(user.getId());
    
    // Then: 验证
    assertNotNull(found);
}
```

### 2. 测试之间有依赖

```java
// 差的实践：test2 依赖 test1 的执行结果
private static Long userId;

@Test
void test1_CreateUser() {
    User user = userService.createUser(new User());
    userId = user.getId();  // 全局变量，test2 会用到
}

@Test
void test2_GetUser() {
    User user = userService.getUser(userId);  // 依赖 test1
    assertNotNull(user);
}

// 好的实践：每个测试独立
@Test
void testGetUser() {
    // 自己准备数据
    User created = userService.createUser(new User());
    User found = userService.getUser(created.getId());
    assertNotNull(found);
}
```

### 3. 不清理测试数据

```java
// 差的实践：测试后数据残留
@Test
void testCreateUser() {
    userService.createUser(new User("test"));
    // 没有清理，影响其他测试
}

// 好的实践：使用 @Transactional 自动回滚
@Test
@Transactional
void testCreateUser() {
    userService.createUser(new User("test"));
    // 测试结束后自动回滚
}
```

## 测试检查清单

在提交代码前，确认以下事项：

- [ ] 所有测试通过（`mvn test`）
- [ ] 测试覆盖率达标（核心业务逻辑 ≥ 80%）
- [ ] 测试使用 H2 内存数据库（单元测试）
- [ ] 测试命名清晰，使用 `@DisplayName`
- [ ] 测试遵循 Given-When-Then 结构
- [ ] 测试覆盖正常场景、边界条件、异常场景
- [ ] 测试相互独立，无依赖关系
- [ ] 测试数据自动清理（`@Transactional` 或 H2 内存模式）
- [ ] 无测试反模式（外部依赖、数据残留）
