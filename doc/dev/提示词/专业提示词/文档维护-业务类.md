# 文档维护（业务类）

面向业务系统项目。与全局提示词配合使用，专管 PRD、specs、流程文档与 README 的维护与同步。

## PRD（产品需求文档）

- 全项目只有一份总文档，大而全，覆盖所有业务域
- 无版本概念：不建 v1/v2、不留历史快照、不加日期后缀、不写变更记录章节
- 需求变化就地修订到与产品当前实际一致，旧表述直接替换，不与新表述并列保留
- 按业务域/功能模块分章节；新需求先找归属章节，无归属才新建

## specs（规格文档）

- 允许分支、版本、迭代概念，可多份并存
- 每份开头标明适用范围（版本/分支/迭代）与对应的 PRD 章节
- 废弃的 specs 标记状态，不删除，保留可追溯性
- specs 描述"当前范围内怎么做"，PRD 描述"要什么"；同一规则不在两处重复

## 代码改动同步

改动业务逻辑即触发，同步更新受影响文档，缺一不可：

1. 流程文档：业务流程、状态流转、时序、异常分支
2. README.md：所改模块的 + 项目根的
3. PRD 对应章节：实际行为与需求描述不一致时
4. specs 对应条目：接口、字段、校验规则、状态机变化时

需更新：
- 业务流程/状态流转变化
- 对外接口、请求响应字段、错误码变化
- 校验规则、计算规则、权限规则变化
- 配置项、部署方式、依赖服务变化

无需更新：
- 内部实现优化、重构（对外行为与流程不变）
- 测试、格式、注释
- 用法不变的版本升级

## 更新方式

- 按原文档结构就地重整，不只在末尾追加
- 不硬编码版本号，用"最新稳定版""查看构建文件获取版本"等表述
- 流程文档用图（流程图/时序图/状态图）+ 关键节点说明，不用长段落复述代码
- 改动跨多模块则逐个更新模块 README；存在模块组聚合 README 时一并核对

## 完成前自查

- [ ] 流程文档与改动后的实际逻辑一致
- [ ] 所改模块 README 与根 README 已更新
- [ ] PRD 无版本化痕迹，且与当前行为一致
- [ ] specs 已标明适用范围，与 PRD 无重复规则
- [ ] 无硬编码版本号
